Streaming Materialized Views with Atlas Stream Processing

1. Introduction to Streaming Materialized Views (SMV)

A Streaming Materialized View (SMV) is a continuously updated, pre-computed collection in MongoDB Atlas populated by an active Atlas Stream Processing (ASP) processor. While traditional views are computed at read-time and "On-Demand" views are point-in-time snapshots, an SMV is perpetually synchronized. It represents a paradigm shift from manual data rollups to change-driven, sub-second latency state management.

By adopting SMVs, organizations eliminate the "DIY streaming tax"—the hidden cost and engineering overhead of gluing together fragmented tools like Kafka, Flink, and external databases. In the MongoDB ecosystem, the streaming engine and the operational data store (ODS) are unified.

Comparison: On-Demand vs. Streaming Materialized Views

Feature	On-Demand Materialized Views	Streaming Materialized Views (SMV)
Update Trigger	Manual or Scheduled (Cron)	Change-driven (Continuous)
Latency	High (Minutes to Days)	Sub-second to Low-second
Data Freshness	Point-in-time / Stale	Perpetually Synchronized
Operational Effort	Fragmented ETL / Brittle Scripts	Unified ASP Control Plane

The Competitive Landscape: Why ASP?

For technical architects, selecting a streaming platform involves balancing specialized power against operational pragmatism. While purpose-built streaming databases like Materialize lead in automatic retraction logic, MongoDB ASP is the superior choice for organizations seeking native integration and the elimination of the "CDC tax."

2. Core Paradigms and Strategic Advantages

The "Integrated vs. Fragmented" Narrative

Traditional architectures rely on "brittle bridges"—external connectors that act as single points of failure between storage and processing. Atlas Stream Processing provides an Integrated Platform, removing the need for external CDC connectors, separate security models, and the operational burden of managing disparate distributed systems.

Tunable Latency: SMV vs. CMV

Architects can tune ASP pipelines to meet specific operational or analytical requirements:

* Streaming Materialized Views (SMV): Focused on low latency (sub-second). These power live dashboards, gaming leaderboards, and real-time equipment status.
* Continuous Materialized Views (CMV): Focused on high throughput. These prioritize write efficiency for large-scale ingestion (e.g., nightly rollups) with eventual consistency.

3. Prerequisites and Database Configuration

To maintain accurate state in a materialized view, the source database and pipeline must be configured to provide "Pre-image" data—the state of a document before a change occurred.

1. Database Requirement: You must enable changeStreamPreAndPostImages on the source collection. Without this, delta calculations for updates and deletes are impossible.
2. Pipeline Source Configuration: The $source stage requires three critical settings for delta reliability:
  * initialSync: {enable: true}: Establishes a baseline by processing existing data.
  * fullDocument: "updateLookup": Retrieves the current post-image of the document.
  * fullDocumentBeforeChange: "whenAvailable": Accesses the pre-image data required for retracted values.

4. The SMV Implementation Pattern: Delta Logic

Because ASP does not yet handle retractions natively, developers must implement Delta Logic. This ensures that if a document is updated or deleted at the source, the materialized aggregate is correctly adjusted.

Using a $switch statement on operationType, we calculate a _delta value:

* Insert: The new value is added.
* Update: The delta is calculated as Post-image - Pre-image.
* Delete: The pre-image value is multiplied by -1 to mathematically retract the contribution.

{
  $addFields: {
    "_delta": {
      "$switch": {
        "branches": [
          { "case": { "$eq": ["$operationType", "insert"] }, "then": "$fullDocument.value" },
          { "case": { "$eq": ["$operationType", "update"] }, 
            "then": { "$subtract": ["$fullDocument.value", "$fullDocumentBeforeChange.value"] } },
          { "case": { "$eq": ["$operationType", "delete"] }, 
            "then": { "$multiply": ["$fullDocumentBeforeChange.value", -1] } }
        ],
        "default": 0
      }
    }
  }
}


5. Operational Data Store (ODS) Patterns

1. Insert-only: Used for additive logic in append-only streams (e.g., clickstreams).
2. Update-aware: Uses the delta-based adjustments defined above to maintain aggregate parity when source documents are modified.
3. Delete-aware: Uses pre-images to subtract values from running totals, ensuring the ODS doesn't contain ghost data from deleted records.

6. Technical Constraints and Workarounds

The Windowing Barrier

Current versions of ASP require that all $group operations reside within a windowing stage (e.g., $tumblingWindow). This acts as a mandatory "wrapper" for stateful processing. Global, windowless aggregation is a high-priority "Market Unlocker" currently in development.

Physical Delete Propagation

While $merge traditionally replaces or inserts documents, physical removal of a document from a view requires specific strategies:

* Soft-Delete Pattern: Set a _deleted: true flag in the $merge stage.
* TTL Indexes: The preferred method for cleaning up views. Set a Time-to-Live index on the target collection to expire stale data automatically.
* Conditional Merge: Use a $cond expression within the $merge stage to execute a "delete" action when the operationType is "delete".

7. Reference Implementation: Solar Device Aggregator

This implementation handles real-time aggregation for industrial IoT workloads, such as 29 million power meters reporting data every second. It uses the Delta Logic pattern to ensure that if a faulty sensor reading is updated or deleted, the hourly total remains accurate.

const solarPipeline = [
  {
    $source: {
      connectionName: "Cluster01",
      db: "iot",
      coll: "power_meters",
      initialSync: { enable: true },
      config: { 
        fullDocument: "updateLookup", 
        fullDocumentBeforeChange: "whenAvailable" 
      }
    }
  },
  {
    $addFields: {
      "_delta": {
        "$switch": {
          "branches": [
            { "case": { "$eq": ["$operationType", "insert"] }, "then": "$fullDocument.watts" },
            { "case": { "$eq": ["$operationType", "update"] }, 
              "then": { "$subtract": ["$fullDocument.watts", "$fullDocumentBeforeChange.watts"] } },
            { "case": { "$eq": ["$operationType", "delete"] }, 
              "then": { "$multiply": ["$fullDocumentBeforeChange.watts", -1] } }
          ],
          "default": 0
        }
      }
    }
  },
  {
    $tumblingWindow: {
      interval: { size: 1, unit: "hour" },
      pipeline: [
        {
          $group: {
            _id: "$fullDocument.device_id",
            total_watts: { $sum: "$_delta" },
            reading_count: { $sum: 1 }
          }
        }
      ]
    }
  },
  {
    $merge: {
      into: {
        connectionName: "Cluster01",
        db: "analytics",
        coll: "device_hourly_stats"
      },
      // Conditional logic: if the source was a delete, we can delete the view entry
      // or replace it with the adjusted aggregate.
      whenMatched: "replace",
      whenNotMatched: "insert"
    }
  }
];

// Deploy with a Dead Letter Queue (DLQ)
sp.createStreamProcessor("solar_agg_processor", solarPipeline, { 
  dlq: { connectionName: "Cluster01", db: "analytics", coll: "solar_errors" } 
});


Management and Monitoring

Monitor processor health using sp.solar_agg_processor.stats(). The primary health indicator is dlqMessageCount; any value above zero indicates data that failed to process and requires intervention.

8. Best Practices for Production

1. Dead Letter Queues (DLQ): Always configure a DLQ. In high-volume environments (e.g., 100 billion trades over 5 years), losing a single event due to a schema mismatch can corrupt your materialized view's integrity.
2. The Canonical Pipeline Principle: Treat ASP pipelines as portable JSON documents. Store them in Git and manage them via Terraform to ensure your streaming infrastructure is versioned and reproducible.
3. Connection Planes: Clearly distinguish between the Control Plane (using the sp object to manage processors) and the Data Plane (using standard MongoDB drivers to query the resulting Materialized View).
4. Idempotency: Ensure your $merge operations are idempotent. This allows the processor to restart or resume without creating duplicate data in your Operational Data Store.
