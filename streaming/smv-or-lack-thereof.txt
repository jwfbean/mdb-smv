Atlas Stream Processing: materialized views (or lack thereof)
What is a view?
A view is just a named query. MongoDB supports views.
db.createView(“bigOrders”, “orders”, [{$match: {$gt: [“$cost”, 100]}}])
…
db.bigOrders.find()
When you run db.bigOrders.find(), the specified query executes on the input collection.
In postgres or SQL Server:
CREATE VIEW big_orders AS
select * from orders where cost > 500
…
select * from big_orders
What is a materialized view?
A “materialized view” is like a view, but it persists its output in a collection.
Different systems do different things. In Postgres, a materialized view’s output must be explicitly refreshed. In SQL Server the output is incrementally maintained and refreshed when a query comes in.
My query
select * from orders where cost > 500
My materialized view in Postgres or SQL Server
CREATE MATERIALIZED VIEW big_orders AS
select * from orders where cost > 500
My MongoDB query
db.inputColl.aggregate([{$match: {cost: {$gt: 500}}}])
sp.createStreamProcessor(“bigOrders”,
[{$match: {cost: {$gt: 500}}}], // Note this is the same query!
{input, output}
)

ASP Today: What works? What doesn’t work?
Below we discuss what does and doesn’t work for building “materialized views” using today’s ASP features.
Things that work
✅Use ASP to continuously copy a MongoDB collection to another cluster
I have a MongoDB collection I want to replicate to another cluster. I want to replicate the initial content of the collection, and any inserts, updates, and delete operations after that. Below is how I can do that with ASP. The “view” I’m materializing in this case is:
db.createView(“view”, “inputColl”, [])
sp.createStreamProcessor(“replicator”, [
{
$source: {
connectionName: “cluster1”,
db: “db”,
coll: “inputColl”,
config: {fullDocument: "required"}
initialSync: {enable: true}
}
},
{ $replaceRoot: { newRoot: {$cond: {if: isDeleteExpr, then: "$documentKey", else: "$fullDocument"}}}},
{
$merge: {
into: {
connectionName: “cluster2”,
db: outputColl.getDB().getName(),
coll: outputColl.getName()
},
whenMatched: {$cond: {if: isDeleteExpr, then: "delete", else: "replace"}},
whenNotMatched: {$cond: {if: isDeleteExpr, then: "discard", else: "insert"}}
},
}
]
For brevity in the examples below, we just use $source, $replaceRoot, and $merge instead of the full stages defined above.
✅Continuously copy a collection– with some extra fields
Similar to the above, but now I want to add a field in my output. This “view” in this case is:
db.inputColl.aggregate([{$addFields: {foo: {$add: [“$bar”, “$baz”]}}}}])
sp.createStreamProcessor(“replicator”, [
$source,
$replaceRoot,
{ $addFields: { foo: {$add: [“$bar”, “$baz”]} } },
$replaceRoot
])
Materialize an aggregation on the past N days worth of data
Things that don’t work (without a ton of extra syntax)
❌$match doesn’t work
Suppose I want to use ASP to materialize a view like:
db.createView(“bigOrders”, “orders”, [{$match: {cost: {$gt: 5}}}])
Today, if you want to use ASP to create a “materialized view” for this… it looks something like the below. Look how complicated the below pipeline is!
sp.createStreamProcessor(“bigOrdersProcessor”, [
// the input
{ $source: { connectionName, db, coll: "orders" } },
// update & delete handling
// turn updates into: delete pre-image followed by insert post-image
{
$set: {
data: {
$cond: [
{$eq: [{$meta: "stream.source.operationType"}, "update"]},
[{image: “$fullDocumentBeforeChange”, op: “delete”}, {image: “$fullDocument”, op: “insert”],
[{image: “$fullDocument”, op: {$meta: “stream.source.operationType”}}]
]
}
}
},
{ $unwind: “$data” },
{ $replaceRoot: {newRoot: “data” }},
{ $setStreamMeta: {“stream.opType”: “$op”}},
{ $replaceRoot: {newRoot: “image”}},
// the actual view query
{ $match: { cost: {$gt: 5 }} },
// the output
{
$merge: {
into: {coll: "bigOrders"},
whenMatched: {$cond: [{$eq: [{$meta: "stream.opType"}, "delete"]}, "delete", "replace"]},
whenNotMatched: "insert"
}
}
]
The below seems like it would work. But what if the source collection updates the “cost” of a document from 5 to 1! What about deletes!
sp.createStreamProcessor(“bigOrdersProcessor”, [
$source: {read from inputColl},
$replaceRoot,
{$match: {cost: {$gt: 5}}}
$merge: {insert or delete on bigOrders collection}
])
❌$lookup
Suppose I want to use ASP to materialize a view like:
db.inputColl.aggregate([{$lookup: {from: “lookupColl”}}])
The below seems like it would work. But the output won’t be updated when the lookupColl changes!
sp.createStreamProcessor(“replicator”, [
$source,
$replaceRoot,
{ $lookup: { from: { connectionName: “cluster1”, db: “db”, coll: “lookupColl” } } }
$merge
])
❌$group
Suppose I want to use ASP to materialize a view like:
db.inputColl.aggregate([{$group: {_id: “$customerId”, totalCost: {$sum: “$cost”}])
This really doesn’t work in ASP without a lot of trickery.

Step 1: ASP materialized views
sp.createMaterializedView(
"bigOrdersProcessor",

{
materialize: {
source: {connectionName: "atlas1", coll: "orders"},
sink: {connectionName: "atlas2", coll: "bigOrders"},
freshness, …
}
}
)
Step 2: stateful mat views
sp.createStreamProcessor("totalBigOrderCostByCustomer",
[
{$match: {cost: {$gt: 100}},
{$group: {_id: “$customerId”, {total: {$sum : “$cost”}}
],
{materialize: {input: {connectionName: "atlas1", coll: "orders"}, output: {connectionName: "atlas2", coll: "totalBigOrders"}}}
)
Step 3: multi-input mat views
sp.createStreamProcessor("bigOrdersFromCustomersNamedKenny",
[
{$match: {cost: {$gt: 100}},
{$lookup: { from, localField, foreignField, as: “customerDetails” }},
{$match: {customerDetails: “kenny”}}
],
{materialize: {input: {connectionName: "atlas1", coll: "orders"}, output: {connectionName: "atlas2", coll: "totalBigOrders"}}}
)
Step 3.5: transactions and exactly-once semantics
Step 4: mat views on core server
db.createMaterializedView("bigOrders",
[ {$match: {cost: {$gt: 100}} ],

)
